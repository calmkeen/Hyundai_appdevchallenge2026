# CarCue 개발 의뢰서

기준일은 2026년 11월 13일이다. 이 문서는 다른 개발 세션에서 CarCue를 실제 앱으로 구현하기 위한 작업 지시서다. 제공된 제안서의 기능과 디자인을 유지하되, 화면만 재현하지 말고 차량 상태 조회부터 안내, AI 질문, 번역, 이용 종료까지 실제로 이어지는 앱을 만든다.

개발의 중심은 **외국인이 지금 이용하는 차량의 상태와 사용법을 익숙한 언어로 이해하도록 돕는 Pleos 차량 앱**이다. 대상은 국내외 외국인 차량 이용자이며, 렌터카·제주·관광객으로 한정하지 않는다. 관광 추천이나 경로 최적화가 핵심 기능이 되어서는 안 된다.

## 1 개발자가 먼저 이해해야 할 제품

사용자는 차의 기본 조작을 알아도 차종과 판매지역이 달라지면 충전 규격, 조작 위치, 표시 문구, 장착 옵션이 낯설 수 있다. 차량에서 문 열림이나 지원 경고 정보가 전달됐을 때 그 뜻과 확인할 내용을 찾는 일도 어렵다.

CarCue는 다음 흐름을 제공한다.

1. 이용할 차량의 차종·연식·판매지역·장착 사양을 확인한다.
2. 읽기 편한 언어를 고른다.
3. SDK로 읽을 수 있는 현재 차량 상태를 확인한다.
4. 확인이 필요한 항목에서 해당 차량의 설명으로 이동한다.
5. 잘 모르는 내용은 AI에 질문하고, 원문과 번역을 함께 본다.
6. 해결되지 않으면 차량별 공식 지원 안내를 확인한다.
7. 이용을 마치면 선택한 언어와 질문·대화를 정리한다.

대표 상황은 ‘앞좌석 왼쪽 문이 열린 상태를 받음 → 열린 문 위치 표시 → 해당 차량의 문 관련 안내 → 상태 다시 확인 → 필요한 경우 공식 지원 안내’다. 상태와 매뉴얼을 연결하는 기능을 제품의 중심에 둔다.

## 3 구현 범위와 우선순위

### 첫 번째 완료 범위

다음 기능을 모두 구현 대상에 포함한다. 다만 실제 연동과 품질 검증은 작은 흐름부터 순서대로 완성한다.

- 차량 프로필 확인과 안내 언어 선택.
- 차량 앱의 홈, 상태 목록, 상태 상세, 관련 가이드 이동.
- 최소 하나의 실제 SDK 상태에 대한 지원 확인, 최초 조회, 변경 알림, 화면 갱신, 구독 해제.
- 배터리·연료·문·지원 경고·타이어 저압 항목을 추가할 수 있는 공통 구조.
- 차종·연식·판매지역·옵션별 가이드 선택과 검색.
- 검수된 매뉴얼을 바탕으로 한 텍스트 AI 질문과 답변 출처 표시.
- 질문·답변·가이드 번역과 원문 보기.
- 연결 실패, 미수신, 미지원, 오래된 값의 구분과 저장된 기본 안내.
- 차량 UX 제한 반영과 이용 종료 시 기록 정리.

상태 연동의 첫 가이드는 실제 수신 가능한 문 상태와 연결한다. 기본 사용법 검증 주제는 충전, 좌석과 거울, 화면과 표시등이다. 이 세 가지는 **안내 주제**이며 지원 언어를 세 개로 제한한다는 뜻이 아니다. 모든 안내는 선택 차량의 공식 자료를 확인한 뒤 게시한다.

### 함께 설계하되 별도 완료로 구분할 범위

QR은 차량 프로필의 가이드를 여는 수단이다. 프로필 ID를 담은 딥링크 처리와 잘못된 ID 처리는 초기 앱에 포함한다. 실제 휴대폰 카메라로 스캔한 뒤 열리는 안내 경험은 모바일 웹 또는 별도 모바일 클라이언트로 이어갈 수 있게 설계하고, 초기 차량 앱 완료와 별도로 검증한다.

휴대폰에는 Pleos Vehicle Service가 없으므로 차량 SDK를 직접 호출할 수 있다고 가정하지 않는다. 휴대폰에서 차량 상태를 보는 기능에는 인증된 차량 연결과 서버 중계가 별도로 필요하다. QR을 스캔했다는 이유만으로 차량 상태 접근권을 주지 않는다.

### 후속 기능

휴대폰과 차량의 인증 연결, 지원 차종 확대, 더 많은 상태 항목, 음성 안내, 여행·관광·내비게이션 연계, 실제 배포와 사전 탑재 협의는 후속 범위다. 지금의 주요 기능을 밀어내며 먼저 만들지 않는다.

초기 버전에는 차량 문 열기, 잠금, 충전 시작 등 제어 API를 연결하지 않는다. 고장 원인 진단, 모든 DTC 접근, ‘운전해도 안전하다’는 판정도 제공하지 않는다.

## 4 실행 환경과 개발 구조

기존 저장소에 합리적인 구조가 있으면 유지한다. 새로 구성해야 한다면 다음을 기본안으로 사용한다.

| 영역 | 기본안 |
| --- | --- |
| 차량 앱 | Kotlin, Jetpack Compose, ViewModel, Coroutines와 StateFlow |
| 앱 데이터 | Repository를 통해 SDK·서버·저장 안내를 접근 |
| 저장 | Room 또는 기존 로컬 저장 구조. 질문과 가이드 캐시를 분리 |
| 서버 | FastAPI, Pydantic, 초기 SQLite. 저장소 추상화로 교체 가능하게 구성 |
| AI | 서버에서 OpenAI Responses API 호출. 모델은 환경설정으로 선택 |
| 응답 형식 | 검증 가능한 JSON Schema와 서버 측 출처 검증 |
| 통신 | 앱은 CarCue 서버와 통신. OpenAI API 키를 APK에 넣지 않음 |

공식 샘플의 확인된 기준은 Vehicle SDK 2.3.2, Vehicle Service 2.3.22, Pleos Connect v2.1 AVD와 Android 14다. 샘플의 빌드 기준은 JDK 17, Gradle 8.10.2, AGP 8.8.2, Kotlin 2.0.0, compileSdk/targetSdk 35다. 이 조합을 호환성 확인의 출발점으로 삼되 기존 프로젝트와 실제 제공 SDK를 먼저 점검한다. 샘플의 minSdk 23을 제품의 배포 조건으로 복사하지 말고 Pleos 제품 앱 요구사항인 API 28 이상을 별도로 확인한다.

일반 Android 에뮬레이터와 Pleos 전용 AVD를 구분한다. UI 테스트용 Mock 구현과 실제 SDK 구현을 명확히 분리한다. Mock 상태가 실제 차량 정보처럼 보이지 않게 개발 모드 표시를 둔다.

예상 구조는 다음과 같다. 작은 프로젝트에서는 별도 Gradle 모듈 대신 패키지로 시작해도 된다.

## 5 차량 프로필과 언어를 분리할 것

차량 프로필에는 제조사, 모델 코드, 연식, 판매지역, 동력 종류, 확인된 옵션, 적용 가능한 매뉴얼 버전이 들어간다. 선택 언어는 별도 필드다. 영어를 선택했다고 미국 사양의 안내로 바꾸지 않는다. IONIQ 5와 IONIQ 5 N, 다른 연식과 판매지역의 문서를 섞지 않는다.

프로필 ID는 사용자가 확인할 수 있어야 한다. 차량 사양을 SDK에서 모두 자동 판별할 수 있다고 가정하지 않는다. 초기에는 운영자가 등록한 프로필을 앱의 차량 목록 또는 QR로 선택하고, SDK에서 얻을 수 있는 차량 정보가 있으면 보조 확인에 사용한다.

프로필이 불명확하면 해당 사양의 조작 절차를 임의로 보여주지 않는다. 먼저 차량을 다시 선택하게 한다. 이때도 일반적인 메뉴 탐색은 가능하게 하되, 다른 사양의 안내를 해당 차량의 안내처럼 표시하지 않는다.

## 6 Vehicle SDK 구현 지시

### 확인된 항목과 확인할 부분

| 항목 | 공식 문서에서 확인한 API | 제품에서의 처리 |
| --- | --- | --- |
| 배터리 잔량 | `checkEvBatteryStateOfChargeCapabilities`, `getEvBatteryStateOfCharge`, `registerEvBatteryStateOfCharge`, `unregisterEvBatteryStateOfCharge` | 지원 여부와 값·단위를 확인한 뒤 잔량 표시 |
| 연료량 | `checkFuelPercentCapabilities`, `getFuelPercent`, `registerFuelPercent`, `unregisterFuelPercent` | 내연기관 등 해당 차량에서 지원될 때 표시 |
| 문 위치 | `checkDoorPositionCapabilities`, `getCurrentDoorPosition`, `registerDoorPosition`, `unregisterDoorPosition` | 실제 지원 영역별 열림 상태와 위치 표시 |
| 타이어 저압 | `checkLowTirePressureCapabilities`, `checkWheelAreaCapabilities`, `getLowTirePressure` | 저압 여부 표시. 실제 공기압 숫자나 PSI 제공으로 확대 해석하지 않음 |
| 경고등 | `checkTelltalesCapabilities`, `getTelltalesInfo`, `registerTelltales`, `unregisterTelltales` | 지원되는 경고 정보만 해당 차량의 공식 안내와 연결 |

API 이름은 공식 문서에서 확인했다. 정확한 Kotlin 인자·반환 타입, 단위, 영역, 권한과 지원 버전은 다음 세션이 설치된 SDK와 공식 선언에서 확인하고 구현한다. 타이어 저압용 알림 API처럼 확인하지 않은 메서드를 이름만 추측해 만들지 않는다.

SDK 작업 순서는 다음과 같다.

1. SDK를 초기화하고 필요한 도메인 객체를 얻는다.
2. 각 API의 권한과 영역을 확인한다.
3. Capability를 확인하고 성공한 경우에만 해당 읽기를 진행한다.
4. 최초 조회 결과를 앱의 공통 상태 모델로 변환한다.
5. 지원되는 변경 알림을 등록하고 실제 콜백을 받으면 갱신한다.
6. 화면 재진입·수동 새로고침 시 필요한 항목을 다시 읽는다.
7. 동일 Listener와 등록한 영역으로 해제하고, 사용이 끝나면 `Vehicle.release()` 한다.

SDK 초기화가 예외 없이 끝났다는 이유만으로 값 수신이 성공했다고 표시하지 않는다. Listener 등록 성공도 실제 변경 알림 수신과 구분한다. Capability 호출 실패를 ‘미지원’으로 단정하지 않는다.

### 공통 상태 모델

지원 상태와 값 상태를 별도로 관리한다.

- 지원 상태는 `UNKNOWN`, `SUPPORTED`, `UNSUPPORTED`, `CHECK_FAILED`로 구분한다.
- 값 상태는 `NOT_REQUESTED`, `LOADING`, `VALUE`, `UNAVAILABLE`, `ERROR`, `STALE`로 구분한다.
- 연결 출처는 `PLEOS`와 `MOCK`를 구분한다.
- 값과 단위, 물리 영역, 마지막 성공 수신 시각, 마지막 조회 시각, 오류를 별도 필드로 둔다.
- SDK가 측정 시각을 주지 않으면 앱이 받은 시각으로 기록하고, 차량의 측정 시각인 것처럼 표시하지 않는다.

값을 못 읽었다고 `0`, `false`, ‘닫힘’, ‘정상’으로 바꾸지 않는다. 이전 성공값을 남길 수는 있지만 최신값과 구분하고 ‘이전 정보’로 표시한다. 오류나 미수신을 차량 고장으로 표시하지 않는다.

상태별 새로고침·만료 기준은 설정으로 관리한다. 변경 알림은 값이 바뀔 때만 올 수 있으므로 알림이 없다는 이유만으로 연결이 끊겼다고 판단하지 않는다. 재조회 결과와 연결 오류를 함께 사용한다. 초기 진입, 앱 복귀, 수동 새로고침과 활성 화면의 제한된 재조회를 구현하고, 주기를 무작정 짧게 하여 SDK를 반복 호출하지 않는다. 실제 호출 빈도는 AVD 검증 후 기록한다.

`ROW_1_LEFT`는 물리적으로 앞좌석 왼쪽 영역이다. 모든 차량에서 운전석이라고 표시하면 안 된다. 좌우 운전석 차이는 확인된 차량 사양으로만 반영한다. SDK 값 범위도 샘플의 `0..1`을 모든 영역에 공통 적용하지 않는다.

## 7 상태에서 안내로 연결하는 규칙

상태별 안내 연결은 검수 가능한 규칙으로 처리한다. AI가 상태를 보고 임의로 조치 사항을 만들어내게 하지 않는다.

```text
수신한 상태 정규화
→ 해당 차량 프로필과 물리 영역 확인
→ 등록된 상태별 규칙 선택
→ 공식 자료에 연결된 확인 사항 표시
→ 다시 조회 또는 관련 가이드 또는 공식 지원으로 이동
```

문 열림은 문 위치와 관련 설명으로 연결한다. 저압 여부는 지원되는 표시와 해당 차량의 타이어 안내로 연결한다. 경고등은 실제 수신 코드와 매뉴얼의 대응 항목이 일치할 때만 뜻을 설명한다. 연결할 자료가 없으면 ‘이 표시의 설명을 아직 확인하지 못했어요’라고 알리고 원문 매뉴얼·공식 지원으로 이어준다.

경고의 심각도, 정차 필요 여부, 조치 순서는 공식 자료에 있는 내용만 사용한다. AI가 주행 가능 여부나 고장 원인을 단정하지 않게 한다. 초기 버전에서 표시되는 AI 답변은 차량 제어 명령으로 이어지지 않는다.

현재값을 읽는 기능과 문을 닫는 제어 기능을 혼동하지 않는다. ‘현재 상태 다시 확인’은 GET이며 SET을 호출하지 않는다.

## 8 가이드와 국가별 차이

가이드는 정확한 차량 프로필을 기준으로 선택한다. 문서에는 출처 URL, 문서명, 연식·판매지역, 페이지나 절, 버전, 검수 상태를 기록한다. 원문과 번역을 함께 보관하고 수정 시 이전 번역을 재검토한다.

안내 항목에는 기본 설명, 확인 순서, 주의 문구, 단계별 이미지, 참고한 원문, 관련 상태 규칙과 공식 지원 정보가 들어간다. ‘차량마다 다를 수 있다’는 말만 넣고 다른 차종 문서를 사용하면 안 된다.

충전 규격·연결 방법, 단위·표시 문구, 좌우 운전석·조작 위치, 장착 옵션은 국가 자체가 아니라 해당 차량의 판매지역과 사양에 따라 구분한다. 현지 교통법규 안내를 넣으려면 별도 출처와 최신성 관리가 필요하므로 초기 기본 기능으로 확대하지 않는다.

## 9 AI 질문과 번역

질문은 CarCue 서버로 보내고, 서버가 해당 차량에 맞는 검수 자료를 먼저 찾는다. 같은 세션의 앞선 질문과 선택한 가이드·단계를 제한된 대화 맥락으로 유지하되, 프로필 전환·이용 종료 뒤에는 재사용하지 않는다. 입력·대화 길이와 검색 문구 수는 설정으로 제한한다. 초기에는 구조화된 가이드와 키워드 검색으로 시작해도 된다. 검색 품질이 부족할 때 임베딩·벡터 검색을 추가한다. 불필요하게 큰 검색 시스템을 먼저 만들지 않는다.

AI에 전달할 내용은 질문, 선택 언어, 차량 프로필, 필요한 상태의 최소 정보, 검색된 관련 문구다. VIN·정확한 위치·모든 차량 원시 데이터를 기본 전송하지 않는다.

AI 응답에는 다음이 필요하다.

- 사용자의 언어로 된 답변.
- 답변에 사용한 가이드 ID와 원문 출처.
- 관련 가이드 열기, 상태 다시 확인, 공식 지원 보기 등의 허용된 다음 행동.
- 자료 부족, 추가 질문 필요, 일시적 실패를 구분하는 응답 상태.

AI가 만든 출처 ID를 그대로 믿지 않는다. 서버가 이번 검색에서 제공한 자료에 포함되는지 확인하고, 다른 차종·지역 자료를 인용하면 응답을 차단한다. 구조화된 JSON이 맞는 것만으로 답변 내용이 검증됐다고 판단하지 않는다.

질문을 바꾸어 금지된 차량 제어를 요청하거나 자료에 없는 고장 진단을 요구해도, 기능 범위 안에서 관련 원문을 찾고 공식 지원으로 안내한다. 자료가 없는 조작 순서를 추측하지 않는다.

번역은 원문과 대상 언어를 받아 수행한다. 숫자, 단위, 부정 표현, 금지 사항, 순서, 부품명을 바꾸지 않는다. 임의 단위 환산을 하지 않는다. 정적 가이드 번역은 저장해 재사용하고 매번 API로 다시 번역하지 않는다. 질문과 답변의 즉시 번역은 서버 API로 처리한다.

OpenAI API 키와 모델 선택은 서버 환경설정으로 관리한다. 이 채팅의 GPT를 앱이 자동 호출하는 구조로 오해하지 않는다. API 이용 비용과 서버 운영 비용은 별도이며, 요청 한도·출력 길이·재시도 수·캐시를 구현한다.

## 10 다국어 지원

특정 언어 두세 개를 화면 코드에 고정하지 않는다. BCP 47 언어 태그를 사용하는 언어 목록과 국가별 주요 사용 언어 매핑을 데이터로 관리한다. 한국어·영어 화면 자산은 시각적 예시일 뿐 지원 상한이 아니다.

약 50개국을 포괄하는 구체적인 국가·언어 목록은 최신 공식 방한 통계 등을 참고해 확정할 작업이다. 임의의 목록을 ‘방한 상위 50개국’으로 발표하지 않는다. 여러 국가가 쓰는 언어는 공유하고 중국어 간체·번체처럼 실제 안내에 영향을 주는 차이는 구분한다.

UI 문자열과 안내 콘텐츠의 번역 상태를 분리하고 `PLANNED`, `DRAFT`, `REVIEWED`, `PUBLISHED`를 관리한다. 검토되지 않은 운영 절차를 검수 완료 번역으로 표시하지 않는다. 지역과 언어를 바꿔도 차량 프로필과 매뉴얼 기준은 그대로 유지한다.

대표 검수에는 한국어, 영어, 일본어, 중국어 간체·번체, 긴 문자열 언어와 RTL 언어를 포함한다. 대표 테스트 언어는 제품 지원 범위를 제한하는 목록이 아니다. 줄바꿈, 글꼴, 화면 확대, RTL과 숫자·단위의 표시를 실제 화면에서 확인한다.

## 11 차량 UX와 연결 실패

플랫폼의 `CarUxRestrictions`와 `ActiveRestrictions`를 받아 기능별 제한을 적용한다. 주행 여부를 임의의 속도·기어 값만으로 대신 판단하지 않는다. SDK 초기화 시점뿐 아니라 제한 변경 콜백에서도 반영한다.

사용자가 직접 긴 안내나 질문 입력을 여는 기능은 주차 중 사용을 기본으로 설계한다. 실제 플랫폼 제한이 우선이다. 제한 상태에서 열려 있던 입력창이나 긴 안내는 규정에 맞게 닫거나 제한 화면으로 전환한다. 알 수 없는 규제 상태에서는 입력·긴 안내를 보수적으로 제한하고 상태를 다시 확인한다. 경고 표시를 임의로 가려도 된다고 가정하지 말고 플랫폼 정책을 확인한다.

앱이 처음 실행됐거나 인터넷이 없어도 차량 프로필과 저장된 검수 기본 안내는 볼 수 있게 한다. AI 실패 시 가짜 답변을 만들지 말고 관련 저장 가이드로 연결한다. 차량 SDK 연결과 인터넷 연결은 별도로 표시한다.

## 12 이용 종료와 기록 정리

회원 가입 없이 시작하는 임시 이용 세션을 기본으로 한다. ‘이용 마치기’를 누르면 현재 세션의 선택 언어, 질문과 답변, 번역 요청 내용, 임시 차량 상태 캐시를 정리하고 SDK Listener를 해제한다. 차량에 등록된 기본 프로필과 공용 가이드 원본은 지우지 않는다. 차량 전체 시스템 언어도 변경하지 않는다. 오프라인 서버 삭제 재시도에 필요한 최소 세션 식별자와 인증 정보만 제한된 로컬 큐에 남길 수 있으며, 질문·답변 본문을 함께 남기지 않는다. 삭제 확인 또는 서버 만료 확인 뒤 해당 큐 정보도 제거한다.

서버의 대화도 삭제한다. 인터넷이 없어 즉시 서버 삭제를 확인하지 못하면 로컬 기록을 먼저 지우고 삭제 요청을 재시도한다. 서버에는 만료 시간을 두며, 원격 삭제까지 확인한 것처럼 표시하지 않는다. 구체적인 보관 시간은 설정으로 관리하고 화면의 설명과 일치시킨다.

로그에는 API 키나 질문 전문을 기본 기록하지 않는다. 요청 ID, 응답 상태, 지연, 토큰 사용량처럼 운영에 필요한 최소 정보를 중심으로 남긴다.

## 13 디자인과 문구

화면은 제공된 SVG와 최신 PDF를 기준으로 한다. 실제 앱에는 휴대폰 테두리, 기울어진 기기 그림, 제안서의 파란 배경판을 넣지 않는다. 그것은 제안서의 목업 표현이다. 버튼과 입력창은 실제 Compose 컴포넌트로 구현한다.

주요 색은 `#2859E8`, 배경은 흰색, 본문은 `#152132`이다. 강조 박스와 주요 버튼은 파란 바탕·흰 글씨를 사용한다. 모든 리스트를 파란 박스로 만들지는 말고 일반 정보는 흰 표면에서 위계와 간격으로 구분한다.

앱은 ‘무엇을 확인할까요?’, ‘아직 차량 정보를 읽지 못했어요’, ‘참고한 안내’, ‘현재 상태 다시 확인’처럼 자연스러운 한국어를 기준으로 한다. ‘이용 지속’, ‘재문의’, ‘이해 정확성’, ‘개인 선택 정리’ 같은 내부 지표·기획 용어를 사용자 화면의 제목으로 쓰지 않는다.

경고를 앱의 장식색으로만 표현하지 않는다. 색에 더해 문구와 위치를 보여주고, 심각도는 차량·공식 자료가 주는 의미를 따른다. 불필요한 애니메이션·자동 줌·과도한 반짝임은 넣지 않는다.

캐릭터는 확정 전이므로 현재 후보를 앱 아이콘이나 코드에 고정하지 않는다. CarCue 워드마크로 진행하고 캐릭터·아이콘 자산을 나중에 교체할 수 있게 한다.

## 14 단계별 납품

1. **환경 확인:** 저장소 구조, 브랜치, SDK·AVD·JDK·빌드 도구, 실제 지원 API를 확인한다. 결과를 `Docs/SDK_CAPABILITY_REPORT.md`에 기록한다.
2. **제품 뼈대:** 프로필·언어·홈·상태·가이드·질문·종료 화면을 실제 내비게이션으로 연결한다. Mock 값에는 명확한 개발 표시를 둔다.
3. **한 상태의 실제 연동:** 권한·Capability·GET·실제 변경 알림·화면 갱신·해제를 끝까지 검증한다. 가능하면 문 상태로 시작하되 AVD 지원 결과를 따른다.
4. **상태와 안내 연결:** 물리 영역, 차량 프로필, 공식 문서 버전으로 규칙을 적용한다. 미지원·미수신·연결 실패도 완성한다.
5. **AI·번역 연결:** 서버 검색·응답 Schema·출처 검증·번역·연결 실패 대응을 구현한다. API 키가 없다면 Mock 서버와 계약 검증을 먼저 끝내고, 실제 연동은 별도로 표시한다.
6. **다국어와 차량 UX:** 언어 목록·레이아웃·번역 검수·주행 제한·이용 종료를 검증한다.
7. **재현 가능한 시연:** 실행 방법, APK, 서버 설정 예시, 시연 영상, 알려진 미지원 항목과 검증 증거를 정리한다.

단계를 끝냈다고 말할 때는 실제 실행 명령과 결과를 함께 기록한다. Listener 등록 성공이나 정적 스크린샷만으로 차량 연동 완료라고 하지 않는다. 실패한 검증은 숨기거나 성공으로 바꾸지 않는다.

## 15 Git와 문서 관리

`main`은 배포 가능한 상태, `develop`은 통합 개발, 기능은 `feature/` 브랜치에서 작업하는 Git flow를 따른다. 기존 브랜치가 있으면 먼저 확인하고 사용자 변경을 덮어쓰지 않는다. 강제 푸시나 기존 이력 재작성은 하지 않는다.

추천 기능 분리는 `feature/project-bootstrap`, `feature/vehicle-status`, `feature/contextual-guide`, `feature/ai-translation`, `feature/localization-session`이다. 각 작업은 관련 기능과 검증을 함께 커밋한다.

인계 문서는 `Docs/`에 복사한다. 다음 결과 문서도 개발 중 유지한다.

- `SDK_CAPABILITY_REPORT.md`: 실제 API·권한·영역·반환값·구독 지원·AVD 결과.
- `IMPLEMENTATION_STATUS.md`: 완료한 기능, 아직 Mock인 기능, 남은 문제.
- `RUNBOOK.md`: 빌드·서버 실행·환경설정·재현 방법.
- `VALIDATION_REPORT.md`: 실행한 검증과 성공·실패 증거.

## 16 완료 기준

완료로 볼 수 있으려면 실제 Pleos 환경에서 하나 이상의 상태를 읽고 변경 알림을 받아 관련 화면을 갱신해야 한다. 차량 사양과 언어가 독립적으로 동작해야 하며, 잘못된 프로필·미수신·미지원·오류·오래된 값이 정상처럼 보이면 안 된다.

관련 가이드는 해당 차량 자료에 연결되고, AI 답변은 서버가 검증한 출처를 보여줘야 한다. 자료가 없거나 API가 실패하면 그 상태와 대체 안내를 보여준다. 번역은 원문을 함께 확인할 수 있어야 한다. 차량 UX 제한과 이용 종료 후 기록 정리도 실제로 확인한다.

상세 화면별 동작은 `SCREEN_SPEC.md`, 데이터·통신 계약은 `DATA_API_SPEC.md`, 검수 시나리오는 `ACCEPTANCE.md`를 따른다. 모든 구현은 이 의뢰서의 제품 범위와 제약을 우선한다.
