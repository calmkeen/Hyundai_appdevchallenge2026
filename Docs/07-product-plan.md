# 제품 기획안: 낯선 차에서도 이어지는 나의 여행

작성: 2026-11-12 · 기획 기준안 · 제품명 및 타깃은 검증 전 가설

## 1. 제안의 중심
**여행자가 준비한 방문 목록을 차 안에서 이어 보고, 낯선 차량의 사용법과 현재 상태를 자신의 언어로 확인한 뒤 기존 내비로 이동을 시작하는 Pleos 앱.**

새 내비게이션이나 범용 관광 챗봇을 만드는 것이 아니다. 여행 목록, 차종 안내, 차량 상태를 따로 찾아야 하는 첫 탑승 경험을 연결한다. 차량 전체의 언어를 바꾸는 기능이나 출고 기본 탑재를 전제로 하지 않는다.

## 2. 누구의 어떤 문제인가
### 초기 페르소나 가설
- 한국을 방문해 처음 현대차·기아 차량을 빌린 영어 사용자.
- 휴대폰으로 갈 장소를 준비했지만 차의 조작 방식과 현지 지명에 익숙하지 않다.
- 제주 여행은 시연 배경 후보이며 실제 대상 차량 보급, 외국인 수요, 사업자 도입 의향은 미확인이다.
- 이번 시제품은 한 차종, 한국어·영어로 한정한다. 해외 판매 차량 고객은 후속 확장 대상이다.

| 문제 가설 | 기존 대안 | 이번에 검증할 개선 |
|---|---|---|
| 매뉴얼에서 필요한 조작을 찾기 어렵다 | 종이/PDF 매뉴얼, 직원 문의, Gleo | 차종·언어가 맞는 핵심 안내를 짧은 카드로 찾을 수 있는가 |
| 여행 목록을 차량에서 다시 입력한다 | 휴대폰 지도 공유, 내비 검색 | 차량 화면에서 장소를 확인하고 순서대로 전달하는 과정이 더 편한가 |
| 차량 수치를 보아도 의미를 모른다 | 계기판, 매뉴얼 | 실제 값·갱신 시각·짧은 설명이 오해를 줄이는가 |

세 문제의 빈도가 충분하지 않거나 기존 서비스로 이미 쉽게 해결된다면 범위를 축소한다. 외국인이라는 이유만으로 차량 사용이 어렵다고 일반화하지 않는다.

## 3. 핵심 시나리오와 화면
### 주차 중 첫 탑승 → 여행 출발
1. **시작:** 차량 앱에서 영어 선택, 시제품에 설정된 차종 확인. QR은 선택적 안내 진입 수단이다.
2. **내 차 이해:** 검수된 안내 카드 3개를 확인한다. 예: 기본 조작 안내, 에너지 상태 읽는 법, 도움이 필요할 때 공식 안내 찾기. 실제 매뉴얼 근거가 확보된 항목만 제공한다.
3. **오늘의 방문 목록:** 시연 지역의 장소 2~3개를 선택하고 주소·좌표를 확인한다. 사용자가 순서를 직접 바꾼다.
4. **출발 전 확인:** 목록과 차량의 실제 수신 상태를 나란히 보여준다. SOC만으로 여행 가능 여부나 충전 필요량을 판정하지 않는다.
5. **내비로 이동:** 선택 장소를 NaviHelper로 전달한다. 요청 실패 시 성공 표시 없이 다시 시도하거나 주소를 확인하게 한다.
6. **이용 종료:** 방문 목록과 사용자 선택을 초기화한다. 차량 앱 내부 언어 선택의 유지 여부는 사용자가 확인한다.

### 화면 구성
- 시작: 앱 언어 / 차종 안내 / 시연 데이터 표식.
- 여행 홈: 오늘의 장소 목록 + 차량 상태 요약 + 차량 안내 진입.
- 방문 목록 편집: 2~3개 장소 / 수동 정렬 / 주소 확인 / 내비 요청.
- 차량 안내: 질문형 카드 / 검수 설명 / 원문 출처·차종·작성 기준.
- 오류·세션 종료: 미지원·오래된 값·전송 실패 구분 / 데이터 초기화.

주행 중 상세 읽기·입력·챗봇은 제한한다. 실제 CarUxRestrictions에 따른 화면 전환을 시험하기 전에는 주행 안전 검증 완료라고 쓰지 않는다.

## 4. QR은 무엇을 연결하는가
| 수준 | 실제 의미 | 이번 범위 |
|---|---|---|
| 정적 QR | 차량 안내 웹페이지나 언어 선택 안내 링크를 휴대폰에서 열기 | 선택적 시연. URL을 열었다고 차량 앱이 연결됐다고 표시하지 않음 |
| 앱 딥링크 | 설치된 앱으로 식별자·화면을 넘기는 진입 | 실행 기기와 핸들러 지원 시험 필요 |
| 폰-차량 페어링 | 사용자 목록을 특정 차량 세션에 안전하게 전달 | 후속. 세션 코드·동의·만료·인증·재사용 방지·종료 처리 필요 |

첫 시제품에서 관광 목록은 차량 앱에 직접 입력한다. 휴대폰의 기존 목록을 자동으로 가져오는 기능은 구현하지 않았다고 분명히 밝힌다. 정적 QR에는 개인정보·VIN·장기 토큰을 넣지 않는다.

## 5. 데이터와 기능 경계
### 관광 목록
- TourAPI는 관광지·음식점 후보 데이터원이다. 언어별 지원, API 키, 이용조건, 이미지 권리, 호출량·캐시 정책을 구현 전에 확인한다.
- 첫 데모는 이용 가능한 고정 장소 데이터로도 가능하다. 고정 자료를 실시간 API 결과로 표현하지 않는다.
- 주변 추천에는 위치 권한과 사용 범위가 필요하다. 처음에는 사용자가 고른 지역 기준으로 제한 가능하다.
- 실제 영업·예약·혼잡을 보장하지 않으며, 추천 근거와 정보 기준일을 표시한다.
- 수동 순서를 내비에 넘기는 것은 동선 최적화가 아니다. 이동시간·경로 계산은 기존 내비에 맡긴다.

### 차량 상태와 가이드
- 연료 또는 SOC 한 항목을 실제 조회한 뒤 지원 여부·수치·시각을 표시한다.
- API 선언 확인은 실제 차량 값 수신 성공과 다르다. SDK 현황은 [검증 기록](03-sdk-verification.md)을 기준으로 한다.
- 알 수 없는 값은 0으로 대체하지 않는다. 문 상태나 속도만으로 탑승·출발 안전을 판단하지 않는다.
- 앱 언어 전환만 제공하며 차량 시스템 언어 변경은 범위 밖이다.
- 차종·트림 자동 식별과 매뉴얼 자동 매칭은 미확인이다. 시제품은 사용자가 확인한 한 차종 자료를 사용한다.

### AI 상담은 후속 기능
차량 매뉴얼의 근거 구절을 검색해 답하는 제한적 도움말로 검토한다. 근거가 없으면 답변을 보류하고 공식 안내로 연결한다. 고장 진단·운행 가능 판정·보증 판단은 제공하지 않는다. 매뉴얼 이용권, 번역 검수, 공급자 비용과 외부 전송 조건을 먼저 확인한다.

## 6. 차별성·사업성 검증
Gleo의 매뉴얼 안내, 지도 앱의 장소 목록과 공유, 내비의 경유지 기능은 이미 존재한다. 개별 기능을 새롭다고 주장하지 않는다.

**차별화 가설:** 첫 탑승 여행자의 차종 이해 → 방문 목록 검토 → 차량 상태 확인 → 내비 요청을 다국어로 연결하면 앱 전환과 반복 입력을 줄일 수 있다. 단, 휴대폰 목록 자동 연동이 없는 초기 시제품에서는 반복 입력 감소를 주장할 수 없다.

| 공식 심사 관점 | 제안의 연결 | 아직 필요한 증거 |
|---|---|---|
| 차량 특화성 | 차종 안내와 실제 상태를 여행 시작 흐름에 연결 | 차량에서 과제 수행, 미지원·주행 제한 시험 |
| 창의성 | 낯선 차 첫 탑승과 여행 준비의 일체화 | 기존 지도·Gleo 조합보다 나은 경험 비교 |
| SDK/API 활용성 | Vehicle 값과 NaviHelper 요청 | 빌드·실제 응답·오류 처리 기록 |
| 사업성 | 렌터카 인수 안내, 이후 해외 신차 고객 온보딩 | 대상 차량 수, 사업자 문의 유형, 설치·배포 비용 조사 |

현대차와의 연결은 차량을 처음 쓰는 고객 경험 개선이다. OEM 사전 설치는 협의 가능한 장기 유통 가설일 뿐, 앱이 자동으로 출고 차량에 탑재되는 것으로 제안하지 않는다. App Market 심사·배포 조건과 렌터카 제휴도 별도 확인한다.

## 7. MVP 결정과 중단 기준
### 우선 구현 제안
한 차종 / 한국어·영어 / 안내 카드 3개 / 장소 2~3개 수동 정렬 / 실제 차량 값 1개 / 검증된 내비 전달 / 초기화.

### 이번 제출에서 제외 제안
폰-차량 인증 페어링, 자유 AI 채팅, 실시간 번역, 자동 경로 최적화, 충전·주행 가능 예측, 전 차종 대응, OEM 사전 설치 구현.

### 단계별 통과 기준
- 차량 값: GET 응답과 UI 갱신 증거가 있을 때만 실제 연동 완료.
- 내비: 요청과 수신 결과를 기록하고 목적지 반영까지 확인. 문서 예제만으로 완료 처리하지 않음.
- 권한/환경: 설치 중인 사용자 환경을 바꾸지 않는다. 승인되지 않은 약관·권한으로 진행하지 않음.
- 연동 실패: 데모 모드와 실제 연동을 분리하고 제출 설명에 한계를 명시. 성공처럼 보이게 대체하지 않음.

## 8. 소규모 사용자 검증 계획
외국인 운전자 또는 한국 차량에 익숙하지 않은 영어 사용자 3~5명을 확보하는 것을 목표로 한다. 아직 모집·시험하지 않았다. 한국인 지인 대리 시험이면 편의성 탐색으로만 기록한다.

| 과제 | 측정 | 오류 관찰 |
|---|---|---|
| 차종 안내에서 지정 조작 설명 찾기 | 완료 여부·시간·도움 요청 | 다른 차종 설명을 믿는지 |
| 장소 3개 순서 조정 후 내비 요청 | 완료 여부·입력 횟수·시간 | 주소·순서 오인, 전송 성공 오인 |
| 정상 값과 확인 불가 상태 설명하기 | 정확히 설명한 항목 | null을 0으로 오해하는지 |
| 이용 종료로 기록 지우기 | 초기화 확인 | 다른 이용자의 목록 잔존 |

기존 매뉴얼+지도+내비 조합과 같은 과제로 비교한다. 가능한 경우 수행 순서를 바꿔 학습 영향을 줄인다. 작은 표본으로 절감률·시장 수요를 일반화하지 않는다. 안내 오해, 성공 오표시, 기록 잔존은 출시 전 수정해야 할 오류로 취급한다.

## 9. 개발 순서와 일정
- 11/12: 기획 기준안, 화면 상태와 데이터 모델 확정 준비. 사용자가 진행 중인 설치에 개입하지 않음.
- 11/13: 로컬 안내·목록·다국어 UI와 실패 상태 구현, 준비된 환경에서 SDK 시험.
- 11/14: 통과한 실제 연동만 연결, 비교 과제와 오류 수정, 영상·기획서 정리.
- 11/15: 새 기능 대신 제출물 일관성·실행·출처 최종 점검. 제출 자체는 별도 사용자 지시 필요.

위 일정은 1인 시제품 제안이며 설치·권한·데이터 이용조건에 따라 축소한다. 상세 개발 원칙은 [개발 계획](04-development-plan.md), 근거 링크는 [근거 기록](06-evidence-and-decisions.md)을 따른다.

## 10. 아직 결정하지 않은 것
제품명, 초기 차종·지역, 실제 대상 사용자, 콘텐츠 권리, 관광 API 접근, SDK 실행 가능성, QR/AI 우선순위는 확정되지 않았다. 본 문서는 논의를 실행 가능한 범위로 정리한 기준안이지 검증 완료 보고서가 아니다.
