# 제품 기획안: 내 언어로 다시 확인하는 차량 이용 가이드

2026-11-12 사용자 방향 전환 반영. 제품명·차종·시장과 효과는 아직 검증 전이다.

## 1. 문제와 제안
처음 차량을 받을 때 설명을 들어도 나중에 필요한 조작이나 상태의 의미를 잊을 수 있다. 언어가 다르면 매뉴얼을 찾거나 직원에게 상황을 설명하는 데 어려움이 생길 수 있다. 이는 검증할 문제 가설이다.

앱은 **짧은 첫 안내 → 필요할 때 상태별 재확인 → 해결되지 않으면 현지 직원 도움**을 연결한다. 계속 읽어야 하는 설명서가 아니라 필요한 순간 다시 찾는 가이드다. 여행·일정 추천은 부가 기능으로 둔다.

## 2. 사용자와 사업 가설
- 초기 페르소나: 한국에서 낯선 차량을 빌린 영어 사용자. 제주·렌터카는 시연 배경 후보이며 최종 시장 확정이 아니다.
- 이용자 가치: 자신의 언어로 사용법과 확인 가능한 상태를 이해하고 도움을 요청하기 쉽게 한다.
- 사업자 가치: 반복 설명 시간과 의사소통 왕복을 줄일 가능성. 실제 절감 효과는 미측정이다.
- 현대차와의 연결: 렌터카와 해외 신차 고객의 첫 차량 이용 경험 개선. 출고 기본 탑재나 제휴는 확보된 것이 아니며 배포·심사·계약 검토가 필요하다.

## 3. 사용자 시나리오
1. 주차 중 앱 언어와 차종을 확인한다. 첫 사용 시 검수 안내 3개를 짧게 제공한다.
2. 이후 앱을 열면 첫 설명을 반복시키지 않고 ‘무엇이 궁금한가요?’ 상황별 안내로 들어간다. 첫 안내도 다시 볼 수 있다.
3. 예를 들어 에너지 표시의 의미를 선택하면 실제 수신한 연료/SOC 값과 시각, 해당 차종의 검수 설명을 보여준다. 값만으로 고장·주행 가능 거리·충전 필요량을 추론하지 않는다.
4. 설명이 맞지 않거나 해결되지 않으면 ‘직원에게 보여주기’로 이동한다.
5. 사용자 선택 질문, 실제 수신 상태, 확인할 수 없는 항목을 영어/한국어로 구분한 카드를 보여준다. 사용자가 직접 보여주는 방식이며 자동 연락·진단은 하지 않는다.
6. 차량 반납·이용 종료 시 방문 목록과 문의 선택 등 세션 기록을 초기화한다.

직원 도움 카드는 ‘문이 고장났다’처럼 원인을 확정하지 않는다. ‘이 조작을 확인하고 싶습니다’, ‘현재 상태를 확인할 수 없습니다’ 등 검수 문구를 쓴다. 긴급 상황에서는 앱 설명에 머물게 하지 않고 공식 도움 안내로 연결한다.

## 4. 화면과 최소 데이터
| 화면 | 내용 | 안전장치 |
|---|---|---|
| 시작 | 언어·차종 확인, 첫 안내 | 실제 지원 차종만 표시 |
| 상황 홈 | 안내 카테고리, 실제 상태 1개 | 확인 불가·오래된 값 구분 |
| 안내 상세 | 검수 설명, 차종·원문 출처 | 고장 진단·운행 허가 금지 |
| 직원 도움 카드 | 사용자 질문과 관측 상태의 양언어 표현 | 자동 외부 전송 금지 |
| 세션 종료 | 선택 및 저장 내용 초기화 | 이전 이용자 기록 잔존 점검 |

상태 데이터는 항목·값·수신시각·지원/오류 상태를 갖는다. 안내 데이터는 차종·언어·검수 텍스트·근거·검수 기준일을 갖는다. 질문 선택과 차량 관측값은 별도 필드로 유지한다.

## 5. MVP와 후속
### P0
한 차종, 한국어/영어, 첫 안내 3개, 상황별 재확인, 실제 상태 1개, 양언어 직원 도움 카드, 초기화. 상세 조작은 주차 중에 제한한다.

### 후속
- 관광 목록·일정·맛집 추천: TourAPI 후보, 이용권·언어·호출량·정보 최신성 확인 필요. 수동 순서 정렬과 자동 동선 최적화는 다르다.
- NaviHelper: 목적지·경유지 전달 문서 확인과 실제 요청/반영 성공을 구분한다. 현재 실행 미검증이다.
- AI: 근거가 있는 매뉴얼 검색형 안내로 제한 검토. 근거가 없으면 보류하며 자유 고장 진단은 하지 않는다. 매뉴얼 이용권·번역 품질·비용·외부 전송 고지 검토가 먼저다.
- 음성: 공개 TTS/STT 시험 가능 안내는 있으나 실제 앱 시험 전이며 필수 시제품 범위가 아니다. 차량 마이크의 외부 STT 전송은 금지한다.

## 6. QR과 언어의 경계
정적 QR은 안내 URL을 열 뿐 인증된 폰-차량 연결이 아니다. 딥링크도 해당 기기의 앱 진입 시험이 필요하다. 실제 페어링에는 세션 인증·동의·만료·재사용 방지·종료 처리가 필요하므로 후속으로 둔다.
앱 UI의 언어 전환과 차량 전체 시스템 언어 변경을 혼동하지 않는다. 시스템 언어 변경은 이번 범위에 넣지 않는다.

## 7. 기존 기능과 비교할 차별성
Gleo 매뉴얼 안내, 번역 앱, 종이/PDF 매뉴얼은 선행 대안이다. 매뉴얼 질의나 다국어 자체를 독점적 차별성으로 주장하지 않는다.

차별화 가설은 **첫 설명 이후 반복되는 이용 상황에서, 확인 가능한 상태와 자기 언어 안내를 잇고 현지 직원에게 상황을 전달하는 흐름**이다. Gleo interface와 LLM SDK는 공모전에서 제공되지 않으므로 직접 연동을 가정하지 않는다.

| 심사 관점 | 기획의 근거 | 추가 검증 |
|---|---|---|
| 차량 특화성 | 차종·실제 상태에 맞는 사용 안내 | 차량별 지원, 주행 제한 |
| 창의성 | 상황 재확인과 직원 도움의 연결 | 기존 대안보다 편한지 |
| SDK/API 활용성 | 읽기 전용 실제 상태 연동 | 응답·권한·오류 증거 |
| 사업성 | 이용자 이해·직원 설명 부담 개선 | 문의 유형, 사용률, 시간 비교 |

## 8. 프라이버시와 실패 처리
VIN·여권·면허·결제정보는 수집하지 않는다. 초기 MVP는 로그인·서버 없이 구성 가능하다. QR에 장기 토큰을 넣지 않는다. 외부 AI를 넣게 되면 질문·차량정보의 전송 범위와 보관·동의를 별도 설계한다.

null을 0으로 바꾸거나 이전 값을 현재 값으로 표시하지 않는다. 지원하지 않는 기능은 미지원으로 표시한다. 직원 카드에 미확인 상태를 사실처럼 담지 않는다. SDK 시험 실패 시 명시적 시연 데이터로 구분하며 실제 연동이라고 하지 않는다.

## 9. 사용자 검증
외국인 또는 낯선 차량을 이용하는 영어 사용자 3~5명과 직원 역할 참여자를 대상으로 하는 소규모 비교 시험을 계획한다. 아직 모집·시험한 것이 아니다.
- 첫 안내 후 특정 상황 안내를 다시 찾기: 성공률·시간·도움 요청.
- 상태 정상/확인 불가를 설명하기: 오해와 올바른 해석.
- 직원에게 질문 전달하기: 의미 일치·추가 확인 횟수·설명 시간.
- 세션 종료 후 기록 확인하기: 잔존 여부.

기존 매뉴얼+직원 설명과 같은 과제를 비교한다. 가능하면 순서를 바꾸고, 직원 설명 시간뿐 아니라 사용자 이해도도 함께 본다. 시간을 줄이려고 필요한 도움 요청을 억제하지 않는다. 작은 편의 표본으로 전체 시장 효과를 일반화하지 않는다.

## 10. 일정과 완료 기준
- 11/12: 차량 가이드 중심 기획·화면·데이터 모델 정리. 사용자의 Android 설치에 개입하지 않음.
- 11/13: 다국어 안내와 도움 카드·실패 상태 구현. 준비된 환경에서만 SDK 시험.
- 11/14: 통과한 실제 상태 연동, 비교 과제와 오류 수정, 기획서·영상 정리.
- 11/15: 기능 추가 대신 실행·출처·제출물 일관성 점검.

빌드, 설치, 서비스 연결, GET, 콜백, UI 반영을 각각 기록한다. 현재 런타임 성공은 미검증이다. 일정은 제안이며 환경·권한에 따라 축소한다. 제출은 별도 사용자 지시 없이 하지 않는다.
